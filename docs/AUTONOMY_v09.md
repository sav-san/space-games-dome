# Анализ исходной версии и автономность

Основа — присланный space-games-dome-main.zip. Из отменённой переработки GUI файлы не переносились.

## Что улучшено другом

- Публикация гипотез переживает изменение части диагностических признаков, с фильтрацией по ещё активным уликам.
- Повреждённый JSON диагностики разбирается частично; неизвестные ссылки удаляются, служебные значения нормализуются.
- Передаётся настройка thinking; диагностический ответ ограничен по длине.

Эти изменения помогают показывать рекомендации. Они не подтверждают безопасность автоматического действия: совпадение одного признака не подтверждает всю старую гипотезу, а исправление confidence не является калибровкой.
Поэтому автономный выбор выполнен отдельным запросом без salvage/sanitize и не использует ослабленную фильтрацию диагностического ответа.

## Как принимается решение

1. Локальная политика формирует только разрешённые кандидаты из текущих показателей.
2. Условия сохраняются минимум 15 секунд, время API меняется. Все используемые источники должны быть свежими; неизвестные обязательные поля блокируют кандидата.
3. В RAG ищутся относящиеся к ситуации материалы. Модель может выбрать только ID уже сформированного кандидата или отказаться.
4. Принимается полный JSON с confidence от 0 до 1, порог 0.95, известными ссылками и обоснованием. Требуется ссылка на разобранный случай, процедуру, каталог неисправностей или техническое описание; одних сырых статистик/рассказа оператора недостаточно.
5. Проверяются права текущего describe_nodes, общие guard-проверки и все условия ещё раз после ответа модели.
6. Перед отправкой сохраняется запись sending. После отправки проверяется физический эффект по новой телеметрии; отказ/таймаут/неподтверждённый эффект останавливают автономность, без автоматического повтора.
7. Публикуется отчёт. Устранение исходной причины не объявляется доказанным по одному успешному переключению.

Порог 0.95 — оценка модели, не доказанные 95% точности. Количество логов, BM25-score и голосование датчиков не используются как статистическая вероятность успеха.

## Границы политики

Автоматически допускаются только cooling turn_on, extraction turn_on и ventilation set_speed +10 пунктов.
Приток усиливается при CO₂ >1200 ppm у всех доступных климатических датчиков одной зоны (минимум два), разбросе ≤300 ppm, задержке ≤5 секунд, исправном фильтре и уже работающем режиме FRESH_AIR/MIXED.
Это консервативные инженерные условия допуска, а не новые уставки оборудования и не доказательство отсутствия общей ошибки датчиков.
Требуются свежие два датчика дыма без дыма, CO ниже 10 ppm, chem_ppm=0 и отсутствие утечки/герметизации. Недостающие поля означают отказ от автономного действия.
Опасности, противоречия, серьёзные энергетические проблемы, удержания, ошибки и отсутствие API-прав блокируют действия.

Автономный запуск производства, home/move, resume, pause/abort, отключение питания, сброс защит, открытие боксов и изменение доверия датчиков не реализованы.
Большой архив логов сохраняется и используется в RAG; он не разрешает произвольные действия модели.

## Отчётность и эксплуатация

Режим включён по умолчанию, явно объявляется при старте и управляется AGENT_AUTONOMY/галочкой GUI.
Отчёты идут пользователю в локальный чат, консоль и JSONL. Сообщения в общий meeting_01 автоматически не отправляются.
Сохраняется команда, основание, confidence, RAG-ссылки, свидетельства и проверка expected/observed/ok.
Успешные действия не повторяются в рамках того же эпизода; неопределённый исход требует ручного разбора и сброса state/autonomy.json при остановленной программе.
Без DeepSeek продолжаются локальная диагностика и мониторинг, автоматических команд нет.

Соревновательный регламент по автономным действиям и объявлению режима нужно согласовать отдельно: эта реализация не является заключением о допуске на соревнование.

## Проверки

91 тест пройден, включая 81 тест исходной версии и 10 новых проверок автономности: недостаточная уверенность, неизвестные RAG-ссылки, смена телеметрии, отсутствие прав, приоритет ручного плана, выключение режима, сохранение блокировки после неопределённого результата и отсутствие повторной команды. API и оборудование реально не вызывались. Оценка уверенности модели на реальных инцидентах не калибрована.
